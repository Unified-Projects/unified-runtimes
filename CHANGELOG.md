# Changelog

All notable changes to this project will be documented in this file.

## [Unreleased]

### Fixed
- **Runtimes created on the default bridge as well as the runtimes network**: `docker::manager::create_container` never set a network mode, so every runtime was created on Docker's default bridge and connected to the configured runtimes network afterwards. A server that binds to its container address bound to the bridge address, which the executor cannot reach, and every runtime had L2 reach to everything else on the bridge. The primary configured network is now the container's `network_mode` at create, so a runtime is only ever on networks the executor put it on; secondary networks are still attached after start. executor-main runs its runtimes with `--network` and never touches the bridge; this matches it.
- **`initialised` set before a runtime had ever listened**: `Runtime::mark_running` set `initialised = 1` as soon as the container was up, and container adoption did the same for any running container. The field therefore said nothing about whether the runtime could serve, and `initialised: 1, listening: 0` is precisely the state that hid the Next.js standalone bind fault for five days and the object-storage error-body fault for a morning. `initialised` is now set only by `Runtime::set_listening`, that is, only when the runtime has answered on port 3000. A runtime that is up but silent reports `initialised: 0` until it answers.
- **A runtime that never listens is no longer left in place indefinitely**: it is marked `failed` at the end of its startup window and removed on the following watchdog cycle, so the next request for that runtime ID builds a fresh one rather than waiting out its timeout against a container that has never answered. Executions arriving during the window still wait on the readiness gate up to their own deadline.
- **`OPEN_RUNTIMES_CODE_PATH` not set on created runtimes**: openruntimes runtime images from September 2026 read `OPEN_RUNTIMES_CODE_PATH` in `/usr/local/server/helpers/lifecycle/extract.sh` to locate the code archive, falling back to scanning `/mnt/code` only when the variable is unset. URT mounted the downloaded source under the runtime's `/tmp` but never advertised its path, so serve-mode runtimes created with a source archive failed with "Code archive not found" unless the caller passed the variable by hand. `apply_runtime_env_vars` now sets `OPEN_RUNTIMES_CODE_PATH` to `/tmp/<mount file name>` whenever `source` is non-empty and the version is not legacy `v2`, matching executor-main 0.29 `Docker.php::createRuntime`. A value supplied in the request `variables` is left untouched. On-the-fly runtime creation from `routes/executions.rs` inherits the fix because it delegates to `create_runtime`.
- **Next.js standalone runtimes bound to their container address and were unreachable**: Next's standalone `server.js` reads `process.env.HOSTNAME || '0.0.0.0'` as its bind address, and Docker seeds `HOSTNAME` with the container identity, which resolves to a single bridge address. The runtime bound there and nowhere else, so the executor on the runtimes network got an immediate connection refusal on every request while the registry reported `status=running, initialised=1, listening=0` indefinitely. `routes/runtimes.rs::apply_runtime_env_vars` now seeds `HOSTNAME=0.0.0.0` into the environment of every runtime container on the modern (non-v2) layout. A caller-supplied `HOSTNAME` still wins, so the per-site variable remains the escape hatch; a blank value is treated as unset. Legacy v2 containers keep the Docker-provided identity. `OPEN_RUNTIMES_HOSTNAME` is a different variable (it carries the executor's hostname to the runtime) and is unchanged, as are the container's own hostname, `/etc/hostname` and the `urt.*` labels.
- **Unix-only permission tests broke the whole test binary on Windows**: `platform.rs`'s test module imports `std::os::unix::fs::PermissionsExt` under a plain `#[cfg(test)]`, so `cargo test -p urt-executor` failed to compile on Windows hosts. Gated on `#[cfg(all(test, unix))]`.
- **Object storage error responses accepted as builds**: `storage/s3.rs::download` never inspected the HTTP status of `get_object`. The `fail-on-err` feature of `rust-s3` is not enabled, so a 503 arrived as `Ok(ResponseData)` and its 207-byte XML body was written to `code.tar.gz`, mounted into a container, and registered as a runtime that was `running` and `initialised` but never listened. Every request to the affected deployment then failed until the hourly idle sweep reaped the entry. All S3 calls now treat any non-2xx as an error naming the operation, the key, the status and the first 300 bytes of the body: `get_object` on both `read` and `download`, `head_object` on `exists` and `size` (a 404 from `head_object` is `false`, not a spurious `true`), and `put_object` and `delete_object`, where a silent non-2xx previously looked like a successful write.
- **Poisoned file-cache entries**: `download` cached whatever it fetched without validating it, and the cache-hit branch copied that straight to `code.tar.gz` without contacting storage, so with the default 30-day TTL a single 503 could serve an error document as a build for a month. Only a body that passes the status and format checks is cached now, and a cache hit is validated before it is served; an entry that fails is deleted and the download falls through to storage.
- **Partial artefacts at the destination path**: downloads are written to a unique `.part` file and renamed into place, so an interrupted or rejected fetch cannot leave a truncated `code.tar.gz` where a container could mount it. `create_runtime` also removes the runtime's tmp folder along with the pending registry entry and readiness notifier when the source fetch fails, so the next request starts a clean create.
- **404s retried as if transient**: `resilience::is_transient_error` matched the substrings `500` and `503` anywhere in a storage error message, so a byte count or an error body quoting an earlier failure could make a missing object look retryable. Storage errors now carry their response status in a fixed `returned HTTP <code>` position, and only the first such token decides: 429 and 5xx retry, everything else fails on the first attempt.
- **Runtime IDs wedged permanently by a cancelled create**: `routes/runtimes.rs::create_runtime` inserted the registry entry as `pending` and then downloaded the source and created the container on the handler future. axum drops that future when the client disconnects, and cancellation is not an error path, so a caller that gave up mid-download (a 180 MB cold start over a slow link, for instance) left a `pending` entry that nothing removed: every later create for that runtime ID hit the existing-runtime guard and returned `RuntimeConflict`, which Appwrite surfaces as a 500, until the entry was deleted by hand. The build now runs on a detached task that the handler only observes, so a disconnect no longer cancels the download or the container creation, and the pending entry is always resolved by the work behind it.
- **A create already in flight is joined instead of refused**: a second create for the same runtime ID now waits on the running build and returns its result, rather than being rejected outright by the conflict guard. A slow first attempt no longer poisons every request behind it.
- **A container that never started held its runtime ID**: `docker/manager.rs::create_container` returned the network-attach and start errors without removing the container Docker had already created. Docker holds a container's name until the container is removed, so the next create for that runtime ID got a 409 from the daemon, and the registry knew nothing about it: `registry.exists` was false, so `create_runtime` skipped `reconcile_existing_runtime_id` and never looked. Recovery took an hourly `cleanup_untracked_managed_containers` pass, which skips keep-alive labelled containers, so a runtime with a keep-alive ID stayed wedged. `create_container` now force-removes the container on either failure, and `run_create` reconciles whatever Docker holds for the name on every create rather than only when the registry has an entry.
- **`sync_status` published runtimes that were still building**: the Docker container exists from the moment `create_container` returns, long before the source is extracted or the build command has run, and `registry::sync_status` overwrote the entry's status with whatever Docker reported. Any `GET /v1/runtimes/{id}` during a build therefore flipped the entry to `running`: executions skipped the readiness gate and spent their timeout talking to `tail -f`, and `cleanup_idle` could reap the entry mid-build. Pending is now a state on the entry (`RuntimeState`), not a value of the status string, and an observed container status is only applied to an entry that its create has already published.
- **Builds took the keep-alive ID from the runtime serving it**: a create with `remove = true` builds an artefact and then deletes its own container, but it registered itself as the keep-alive owner for the length of the build. That revoked the serving runtime's protection from `cleanup_idle`, which could reap it while the build ran. A create that removes its container no longer takes ownership.
- **Maintenance tore down creates that were still running**: the stale-owner sweep in `cleanup_orphaned_keepalive` unregistered any keep-alive owner whose container was absent and removed its registry entry, outside the per-ID lock. A create registers ownership when it inserts its pending entry, which is before the source download, so a maintenance cycle landing in that window left the create to fail at its own `registry.update` and tear down the container it had just built. The sweep now skips pending owners and holds the per-ID keep-alive lock across the check and the removal.
- **Keep-alive lock entries deleted while a task held them**: `KeepAliveRegistry::unregister` removed the ID's mutex from the map, so a task that acquired it afterwards got a fresh mutex and two tasks could run the replacement flow for one ID at the same time. Lock entries are now kept for the life of the process.
- **10s spent stopping the previous keep-alive owner on the create's clock**: replacing a keep-alive owner called `stop_container(previous_owner, 10)` inline before the create returned. Runtime images run `tail -f /dev/null` or `bash -c` as PID 1, neither of which handles SIGTERM, so Docker waited the full grace and then sent SIGKILL. After an executor restart, adoption makes the old container the owner again, so the first create for that keep-alive ID paid the 10s: the likeliest cause of the 10005ms first create in the benchmark run. The previous owner is now removed on a background task once the new runtime is registered, under the keep-alive lock the create already holds, with a 1s grace before the force-remove.
- **Working directory and container left behind on create failure**: the source-download, container-creation, container-startup and temp-path failure branches removed the registry entry but not the runtime's tmp folder, and the temp-base canonicalisation failure returned through `?` without removing the pending entry at all. All create failure paths now go through `abandon_pending_create`, which removes the container if one reached Docker, deletes the working directory, wakes readiness waiters and removes the registry entry.
- **`rust-s3` built without `fail-on-err`**: the feature is now enabled, so a non-2xx arrives as `S3Error::HttpFailWithBody` carrying the status rather than as an `Ok` response whose body happens to be XML. The explicit status checks added alongside stay in place: the feature is a build-time flag on a dependency, and the cost of it being off is an error document mounted into a container. A 404 from `head_object` still reads as absence (`exists` returns `false`, `has_cache` returns `false` for a manifest that has not been written yet) and a 404 from `delete_object` is a no-op, while 429 and 5xx keep their `returned HTTP <code>` shape and stay retryable. The retry loop inside `rust-s3` is switched off at construction: it retried every failure identically, a 404 and a `put_object` included, with whole-second sleeps, which would have added a request and a second to every cache-miss manifest check.
- **Storage keys used the host path separator on Windows**: `LocalStorage::list` returned `builds\runtime\hash\manifest.json`, so `BuildCache` (which matches on `/manifest.json`) found no manifests and its size-bounded cleanup deleted nothing. Keys are now assembled from path components with `/` on every platform.
- **Windows bind-mount sources carried the `\\?\` prefix**: `canonicalize` returns the verbatim form, which the Docker daemon rejects as a mount source. `platform::strip_verbatim_prefix` reduces it to the ordinary form before the runtime's tmp folder is derived from it, keeping the prefix where dropping it would change the path (over the legacy 260-character limit, or a component ending in a dot or a space).
- **Delete and shutdown cleanup were not scoped to the executor**: `DELETE /v1/runtimes/{id}` listed containers by `urt.runtime_id` alone and shutdown cleanup listed everything labelled `urt.managed`, so two executors sharing a Docker daemon removed each other's runtimes (runtime IDs are unique per executor, not per daemon). Both now apply `docker::container::belongs_to_executor`, the same `urt.executor_hostname` check with a name-prefix fallback that adoption and maintenance already used.
- **Shutdown cleanup compared container IDs against the daemon ID**: the self-skip in `cleanup_managed_containers` matched containers against `docker.info().id`, which identifies the engine, not a container, so it never matched anything. It now uses the resolved own container.
- **Executor found its own container by name substring**: the Docker name filter matches substrings and runtimes are named `<hostname>-<runtime id>`, so an executor called `exc1` matched every runtime it had created and took the first. `DockerManager::resolve_own_container` reads the container ID from `/proc/self/cgroup` or `/proc/self/mountinfo` on Linux and confirms it with an inspect; the name filter is only a fallback, and it now excludes `urt.managed` containers, prefers an exact name match and returns nothing rather than guessing between two candidates.
- **Stats collector called `docker.info()` every second**: with 50 runtimes that was one daemon call per runtime plus one for host stats, every second, for a value (total host memory) that does not change while the executor runs. Host stats are refreshed once a minute, immediately after a failed call, and cached in between. Per-container stats were already one-shot rather than streamed.
- **Storage file cache was built and never used**: `main.rs` constructed `StorageFileCache` and passed `None` to the storage backend, so every cold start went to object storage. It is now wired into the S3-backed backends via `from_config_with_cache` and `from_dsn_with_cache`, gated on the cache directory initialising. Only a download that passed the status and archive-format checks is ever written to it, and a cache hit is validated before it is served.
- **S3 downloads buffered the whole object in memory**: `download` collected the body into a `Vec` and then wrote it out, so a 200 MB build cost 200 MB of resident memory on the executor, and the cache branch read it back off disk again. The body now streams onto a `.part` file, is validated by reading only its leading block, and is renamed into place; caching copies the file rather than re-reading it.
- **An unknown runtime ID cost a Docker inspect per request**: an execution for an ID that is neither registered nor being built ends with an adoption attempt, so a scan against nonexistent IDs put one `inspect` per request on the daemon. A failed attempt is now remembered for `URT_ADOPTION_NEGATIVE_CACHE_MS` (default 2000 ms), which bounds how long a container that genuinely appears goes unadopted while turning a scan into one call per name per TTL. A successful adoption clears the entry, and the map is swept of expired entries once it passes 1024 names so a scan over random IDs cannot grow it without bound.
- **A dead runtime container went unnoticed and every execution burned the connect timeout**: when a runtime container exited (in the benchmark, exit 134 from a V8 heap OOM) the registry entry stayed `running` and `listening`, `runtime::protocol` mapped the 5s connect timeout to `ExecutionTimeout` (HTTP 400 `execution_timeout`), nothing was logged above debug, and nothing recovered until the hourly maintenance sweep. Transport failures are now classified from the `reqwest::Error` itself before it is flattened to text: a failed dial (DNS, refused, connect timeout) is `RuntimeUnreachable` (503 `runtime_unreachable`), a request that was sent and got no complete answer in time stays `ExecutionTimeout` but answers 504, and a connection that broke after the request went out (reset, closed mid-response, truncated body) is `RuntimeConnectionFailed` (502 `runtime_connection_failed`) carrying the source chain. Every runtime-side failure is logged at warn with the runtime name, elapsed time and the error's Debug form. On `RuntimeUnreachable` the execution path inspects the container once (per-runtime single-flight with a 2s verdict cache, so a burst of concurrent failures costs one inspect), records the death, and either waits for Docker's restart policy to bring the container back (bounded by 30s and the caller's timeout) and retries the execution once, or removes the container, registry entry and working directory so the on-the-fly create runs when the caller supplied an image and a 404 is returned when it did not. Requests that arrive while a runtime is being checked or restarted fail fast with 503 instead of each dialling into the timeout.
- **Runtime IDs containing `502`, `503`, `504` or `429` had failed executions retried five times**: `resilience::is_transient_error` matched those substrings in the `Network` error text, which contains the runtime URL, so a network error against such a runtime was retried with the user function re-run each time. The `Network` arm is gone; only `RuntimeUnreachable` (nothing was sent) is transient, and the execution path itself repeats a refused dial at most once after 50ms. A connect timeout and anything that failed after the request went out are never repeated.
- **`ExecutionTimeout` answered 400**: the OpenRuntimes executor only returns 400 `execution_timeout` for legacy v2 runtimes and 500 for a v5 curl timeout; neither is a client error. URT now answers 504 for a runtime that accepted the request but did not finish inside the deadline.

### Added
- **Per-runtime lifecycle knobs as request fields with environment defaults**: `startupTimeout`, `inactiveThreshold` and `maxConcurrency` are accepted on `POST /v1/runtimes` and on the on-the-fly create inside `POST /v1/runtimes/{id}/executions` (JSON and both multipart parsers), default to `URT_STARTUP_TIMEOUT_SECS` (60), `URT_INACTIVE_THRESHOLD` (60) and `URT_RUNTIME_MAX_CONCURRENCY` (unlimited), and are echoed on the runtime in `GET /v1/runtimes`. Unknown fields are still ignored, so OpenRuntimes callers are unaffected. The resolved values are written as the container labels `urt.startup_timeout`, `urt.inactive_threshold` and `urt.max_concurrency` (0 meaning unlimited) and read back during adoption, so a runtime keeps its settings across an executor restart.
- **`runtime::RuntimeConcurrency`**: per-runtime admission control behind `maxConcurrency`. Executions beyond a runtime's cap wait up to `URT_EXECUTION_QUEUE_WAIT_MS` and are then refused with the new `ExecutorError::RuntimeAtCapacity` (HTTP 503, type `runtime_at_capacity`) naming the runtime and its limit, instead of piling onto a runtime that cannot keep up. Runtimes with no cap never touch it. The slot map is pruned against the registry on every watchdog cycle.
- **`registry.mark_failed`**: records the executor's verdict on a runtime that never listened, leaving a runtime that has started listening alone. `sync_status` no longer overwrites a `failed` status from Docker, which would otherwise resurrect the entry before it is reaped.
- **Non-listening runtime watchdog** (`tasks::listening_watch`, spawned from `main.rs`): the task that observes whether a runtime ever starts listening, and the only thing that sets `initialised`. See the Changed entry below for what a cycle does. This fault class was previously only visible by reading `listening` out of the registry by hand.
- **`storage::archive`**: validates a downloaded artefact against the format its key implies before anything mounts it. Non-empty plus gzip magic for `.tar.gz`/`.tgz`/`.gz`, zstd magic for `.tar.zst`, a checksum-verified header block for `.tar`, and rejection of XML or HTML error documents for keys with no recognised extension. `storage::download_verified_archive` combines the retrying download with that check and is the single path `create_runtime` uses for source fetches; it deletes the local file when validation fails and returns the verified size.
- **Tests**: unit coverage for status handling, retry classification, cache-hit rejection and atomic writes in `storage/s3.rs`, format and error-document detection in `storage/archive.rs`, and status-aware retry decisions in `resilience.rs`. `tests/integration.rs` gains `mod source_archive_integrity`, which drives an XML body named `code.tar.gz` through the local storage backend and through `POST /v1/runtimes`, asserting that the create fails and leaves no registry entry and no tmp folder.
- **`runtime::CreateTracker`**: records every create for the duration of its build, keyed by container name. Backs both the join-in-flight behaviour and the maintenance reaper. `CreateSlot::drop` publishes a failure when a build task ends without an outcome, so no caller can park on a slot that nothing will resolve.
- **Maintenance reaper for orphaned pending entries** (`tasks::cleanup_stale_pending`): removes pending registry entries that are past `pending_max_age_secs` and have no create in flight, waking any parked readiness waiters first so they get a deterministic 404 rather than waiting out their deadline. Entries whose build is still running are never reaped, however long the build takes. Runs before the untracked-container sweep so a container left by a reaped entry is cleaned up in the same cycle.
- **`Config::pending_max_age_secs`** (env `URT_PENDING_MAX_AGE_SECS`, default 300s): age bound for the reaper above.
- **`Config::max_concurrent_builds`** (env `URT_MAX_CONCURRENT_BUILDS`, default `max(2, num_cpus / 2)`): permits for build-style creates, held on a semaphore of their own.
- **`RuntimeState`**: the lifecycle state of a registry entry, `Pending` until the create that inserted it publishes it. Process-local and not serialised, so the `status` field of the API response is unchanged. `Runtime::publish_status` sets the container status and clears pending in one step; adoption uses it too, since an adopted container has no create behind it.
- **9 tests**: `CreateKind` classification and permit accounting (builds do not draw on the serve pool, a serve permit returns once the container is running, a build permit does not), keep-alive ownership skipped for `remove = true` creates, an observed container status leaving a pending entry alone, the stale-owner sweep skipping a pending create and waiting for the keep-alive lock, and a lock surviving `unregister`. `tests/integration.rs` gains `mod create_path_hardening`, whose three Docker-gated tests cover the container removed after a failed start with the retry succeeding, a read not publishing a pending runtime, and a keep-alive transfer returning without waiting for the previous owner to stop.
- **Tests for the lifecycle policy**: unit coverage for the network mode and hostname in the container create body (`docker::manager`), the pending -> running -> listening -> failed transitions and the lifecycle label round trip (`runtime::runtime`), `mark_failed` and per-runtime idle selection (`runtime::registry`), admission and slot reuse (`runtime::concurrency`), the sweep and its startup windows (`tasks::listening_watch`), label restoration during adoption (`tasks::maintenance`), and request parsing with, without and with null lifecycle fields including a v2 request and unknown fields (`routes::runtimes`). `tests/integration.rs` gains `mod lifecycle_policy` covering a runtime that never listens being marked failed after its window (with `tokio::time::pause`), a per-runtime `startupTimeout` widening it, a failed runtime being listed and then reaped, per-runtime `inactiveThreshold` honoured by idle cleanup, and `maxConcurrency` returning 503 beyond the cap.
- **13 tests**: `runtime::create_tracker` unit tests cover a cancelled caller not aborting the build, a cancelled create leaving no pending entry, a retry joining the in-flight build instead of conflicting, and a panicking build releasing its slot; `tasks::maintenance` unit tests and the `cold_start_wedge` integration module cover reaping orphaned pending entries, leaving in-flight and recent entries alone, waking waiters on reap, and the config knob. None require Docker.
- **`Config::adoption_negative_cache_ms`** (env `URT_ADOPTION_NEGATIVE_CACHE_MS`, default 2000 ms): lifetime of a remembered adoption miss. Zero disables the cache and restores a Docker inspect per request.
- **`runtime::AdoptionNegativeCache`**: the map behind that knob, held on `AppState` and consulted by `readiness::resolve_runtime_with_readiness` before the adoption attempt.
- **`docker::self_container`**: container ID parsing for `/proc/self/cgroup` (cgroup v1, cgroup v2 and systemd scope layouts, plus the Kubernetes paths) and `/proc/self/mountinfo`, and the candidate selection used when neither is available.
- **`docker::container::belongs_to_executor`**: the ownership check, moved out of `tasks::maintenance` so the delete route and the Docker manager can apply it too.
- **`StorageFileCache::put_file`**: caches an artefact already on disk, so a streamed download does not have to be read back into memory to be cached.
- **`platform::strip_verbatim_prefix`**: reduces a canonical Windows path to the form Docker accepts as a bind-mount source; a no-op elsewhere.
- **Tests**: a local endpoint serving canned S3 responses drives `exists` against a 404, `download` against a 503 (no file and no `.part` left behind, error retryable) and against a 200 gzip body, plus the cache being populated only by a validated download. Unit coverage for the adoption negative cache including expiry and the size bound, the cgroup and mountinfo parsers and own-container selection, host-stats refresh scheduling, executor ownership, forward-slash storage keys, and verbatim path stripping. None require Docker.
- **Docker events task** (`tasks::docker_events`, env `URT_DOCKER_EVENTS`, default `true`): subscribes to the daemon's container events (`die`, `oom`, `stop`, `kill`, `destroy`) for `urt.managed=true` containers belonging to this executor and marks the registry entry dead the moment a runtime exits (status, `listening=0`, exit code), then runs the same death handling as the execution path: keep the entry when Docker's restart policy will restart the container, remove everything otherwise. Stops and removals issued by URT itself (delete, idle cleanup, keep-alive replacement, failed creates) are remembered by `DockerManager` for a minute and not counted as crashes. The stream is reopened with 1s to 30s backoff when it ends.
- **Crash-loop protection** (`runtime::health::RuntimeHealth`): per-runtime death history (bounded, with exit codes) and restart backoff of 1s, 2s, 4s ... up to `URT_RESTART_BACKOFF_MAX_SECS` (30) between executor-initiated recreates, measured from the last death. `URT_CRASH_LOOP_THRESHOLD` (3) deaths inside `URT_CRASH_LOOP_WINDOW_SECS` (60) quarantine the runtime for `URT_QUARANTINE_SECS` (300): the container is removed, the registry entry stays visible in `GET /v1/runtimes` with `status: "quarantined"`, `quarantined_until` and `last_exit_code`, executions answer 503 `runtime_quarantined` and creates 409 `runtime_quarantined`, both with a `Retry-After` header and a message naming the last exit code and the expiry. The quarantine clears on expiry, lazily on the next request or by the maintenance sweep. Warn lines name the runtime on every death and on quarantine.
- **Metrics**: `urt_runtime_deaths_total{exit_code}`, `urt_runtime_quarantined_total`, `urt_runtime_unreachable_total`.
- **`restartPolicy` accepts `on-failure:<n>`**: `docker::container::RestartPolicySpec` parses the Docker CLI spelling and the retry cap is passed to the daemon. Bare `on-failure` now retries without limit as Docker does (it used to be silently capped at 3).
- **Tests**: `runtime::protocol` classification tests against local listeners that refuse, close before answering, close mid-body and never answer; `runtime::health` backoff, quarantine, expiry and marker tests under `tokio::time::pause`; restart-policy parsing and default tests; `tasks::docker_events` parsing tests; and `tests/integration.rs` `mod dead_runtime_detection` covering death accounting through a synthetic `die` event, quarantine and its expiry without Docker, plus Docker-gated tests for the fast 503 on a marked runtime, entry removal for a dead runtime, on-the-fly recreate when an image is supplied, 503/409 with details while quarantined, and the events path removing a runtime whose container is gone.

### Changed
- **`tasks::listening_watch` now acts rather than only warns**: it sweeps every 5s instead of 30s, probes each running runtime that has not listened yet (250ms per probe, 8 at a time) and records the ones that answer, so `initialised` flips as soon as a runtime comes up even if nothing executes against it. A runtime past its own `startupTimeout` with no listener is probed once more and then marked `failed`, with a warning naming the runtime, its image and how long it has been running. Failed runtimes are reaped at the start of the next cycle, so the verdict is visible in `GET /v1/runtimes` for a full cycle first. Takes a `ListeningWatchHandles` struct now that it also needs Docker, the keep-alive registry and the concurrency map.
- **Background listening probe after create**: `create_runtime` spawns a probe that watches the new runtime until it listens or its startup window ends. `create_runtime` itself returns exactly what it returned before, and when it returns is unchanged.
- **Idle cleanup measures each runtime against its own `inactiveThreshold`**: `RuntimeRegistry::get_idle` takes the executor default and applies it only to runtimes that carry no value of their own.
- **The container hostname is left to Docker**: `create_runtime` used to set it to a random 32-character hex value, which Docker then mapped to the container's address in `/etc/hosts`. Nothing in the executor reaches a runtime by hostname (every caller uses the container name over the runtimes network), so the value only gave a server another wrong address to bind to. executor-main leaves it unset. The `hostname` field on the runtime object is unchanged, so the API response shape is the same.
- **Adoption takes the executor's lifecycle defaults**: `adopt_container_by_name` and `adopt_existing_containers` take a `RuntimeLifecycle` for containers whose labels predate the knobs.
- **Source archives keep their real extension in the `/tmp` mount**: the mount name is now derived by a single `source_mount_file_name` helper shared by the download path and the `OPEN_RUNTIMES_CODE_PATH` value, so the two cannot drift. `.tar.gz`, `.tgz`, `.tar`, `.sqfs` and `.gz` sources map to `code.tar.gz`, `code.tgz`, `code.tar`, `code.sqfs` and `code.gz` respectively; anything else keeps the previous `code.tar.gz` default. Previously only `.tar` was special-cased and every other source, squashfs included, was mounted as `code.tar.gz`. Build commands that hardcode `/tmp/code.tar.gz` (including the built-in Next.js build command) therefore only work with gzipped-tar sources, which matches executor-main.
- **`tasks::run_maintenance` takes a `MaintenanceHandles` struct** rather than five positional handles, now that it also needs the readiness map and the create tracker.
- **Provider constructors on `S3Storage` take a file cache**: `new_do_spaces`, `new_backblaze`, `new_linode` and `new_wasabi` gain the `Option<Arc<StorageFileCache>>` argument `new_s3_with_cache` already had, and all six share one endpoint-resolution helper. `storage::from_config` and `storage::from_dsn` keep their signatures and pass `None`.
- **Builds and serve-style creates queue separately**: one semaphore covered both, and a create held its permit from the moment the handler started until the build finished, upload and container teardown included. Four concurrent builds on a 4-core host took every permit for up to 600s each, so every cold start queued out and its executions came back as `RuntimeOverloaded`. A create carrying a build command, or one with `remove = true`, now draws on `URT_MAX_CONCURRENT_BUILDS`; everything else draws on the existing `URT_MAX_CONCURRENT_RUNTIME_CREATES` pool and gives its permit back as soon as the container is running, before the readiness wait. Both keep the `URT_RUNTIME_CREATE_QUEUE_WAIT_MS` fast-fail. The request body is parsed before the permit is taken, because the request decides which pool it belongs to.
- **Default `restartPolicy` is `on-failure:3`** for both `POST /v1/runtimes` and on-the-fly creates from executions (it was `no`), so a runtime that exits non-zero is restarted by Docker before URT has to recreate it. An explicit `restartPolicy` in the request still wins. URT's own delete, idle cleanup and keep-alive replacement remove the container outright, which Docker's restart policy does not fight.
- **Registry activity is recorded after a successful execution**, not before the request is sent, so a runtime that only ever fails stops looking busy and becomes eligible for idle cleanup. A runtime found dead loses its `listening` flag, and the port probe runs again when it comes back.
- **`ContainerInfo`** carries `exit_code`, `oom_killed`, the restart policy, its retry cap and `restart_count` from `inspect_container`; `RuntimeRegistry::sync_status` keeps quarantined entries when the container is absent and clears `listening` for any non-running state.

## [0.4.1] - 2026-05-04

### Fixed
- **Bot-scan-induced 30s 504 storm against pending runtimes**: `runtime::readiness::resolve_runtime_with_readiness` previously parked every caller on the runtime's `Arc<Notify>` for the full caller-supplied `req.timeout` whenever the registry entry was in pending state. Bot scanners targeting nonexistent paths (`/.env`, `/.git/config`, `/api`, `/graphql`, `/.DS_Store`, `/ecp/...`) that Appwrite forwards as function executions on a runtime ID currently being built would each block 30s and return `RuntimeTimeout` -> 504. The full caller deadline is no longer the wait bound for callers who did not initiate the build.
- **Readiness map leak on `create_runtime` error paths**: `routes/runtimes.rs::create_runtime` inserted into the `AppState.readiness` notifier map at the start and only removed on the explicit success-path call to `readiness_notify_and_remove`. Any error branch between those two points (registry insert race, container start failure, network attach error, build extraction failure, registry update failure) left the entry in the map; subsequent requests for that runtime ID would park on a `Notify` that nothing would ever wake, blocking until their own deadlines. Every error path now drops the new `ReadinessGuard` which calls `notify_waiters()` and removes the map entry.
- **R1 unknown-ID poll burned 200ms per scan**: the pre-insert race fallback in `resolve_runtime_with_readiness` polled with exponential backoff (10ms -> 20ms -> 40ms) up to a 200ms ceiling for every request whose runtime ID was neither in the registry nor in the readiness map. Reduced to a single ~10ms poll iteration; the legitimate notifier-creation race (notifier appears within ~10ms of request entry) is still covered by the post-sleep branch, with up to 200ms of additional wait once the notifier is observed.
- **`commands` and `logs` routes no longer block on someone else's build**: both routes previously called `resolve_runtime_with_readiness` with the wait path enabled. They now pass `should_wait_for_pending = false` and `adopt = false`, returning `RuntimeNotFound` immediately when the registry entry is pending. Neither route can legitimately wait for a build it did not initiate.

### Added
- **`ReadinessGuard` RAII type** in `runtime::readiness`: wraps the `AppState.readiness` insertion site so any error path between insertion and the explicit success-path notify automatically calls `notify_waiters()` and removes the DashMap entry on drop. Provides `disarm()` for the success path so the explicit removal call remains the single load-bearing operation. Panic-safe; relies only on infallible DashMap and Notify operations.
- **`Config::pending_wait_max_secs`** (env `URT_PENDING_WAIT_MAX_SECS`, default 60s): caps the pending-runtime wait duration independently of the caller's `req.timeout`. Applied as `min(cap, deadline_remaining)` so the caller's deadline still shortens when smaller than the cap; the cap only ever bounds the wait, never extends it.
- **`should_wait_for_pending: bool` parameter** on `resolve_runtime_with_readiness`: routes opt in to waiting only when the caller legitimately owns the build. `routes/executions.rs` passes `!req.image.is_empty()` (creation-style requests wait for their own build); `routes/commands.rs` and `routes/logs.rs` pass `false`. The notify-based wait, R1 race fallback, and adoption path are all preserved for callers that opt in.
- **8 new integration tests** under `tests/integration.rs` `mod regression_pending_wait`: `scan_request_does_not_park_on_pending_runtime`, `legitimate_creation_request_still_waits_on_pending`, `pending_wait_capped_by_config` (uses `tokio::time::pause`), `commands_route_does_not_wait_on_pending`, `logs_route_does_not_wait_on_pending`, `readiness_guard_fires_on_error_path`, `unknown_id_r1_poll_short_circuits_fast`, `bot_scan_concurrent_with_build_does_not_block_build` (50 concurrent scans + live build, asserts all scans 404 in <1s, build completes, scan p99 <500ms).

## [0.4.0] - 2026-04-28

### Fixed
- **Notify-based readiness gate (replaces poll-based fix from 0.3.1)**: `resolve_runtime` now parks waiters on a per-runtime `tokio::sync::Notify` keyed in a new `AppState.readiness` map and wakes them when `create_runtime` transitions the registry entry out of pending. Eliminates per-request Docker `inspect_container` polling on the hot path. Concurrent first-execution storms (50+ waiters) wake from a single `notify_waiters()` call, no fan-out to the Docker daemon. Pre-insert (R1) waiters are handled by a bounded sub-deadline plain-poll fallback.
- **Readiness gate applied to commands and logs routes**: `routes/commands.rs::resolve_runtime` previously returned `RuntimeTimeout` immediately when the registry entry was pending; now waits up to the request `timeout`. `routes/logs.rs::resolve_runtime` previously had a hardcoded 2-second grace window; now uses the validated `timeout_secs` query parameter and the shared readiness helper. Both routes now route through `runtime::readiness::resolve_runtime_with_readiness`.
- **DashMap shard locks no longer held across `await`**: `runtime::registry::sync_status` previously held a `get_mut` shard guard across `docker.inspect_container().await`, serialising every key on the same shard for the duration of the Docker RPC. Restructured to release the guard before the await and re-acquire only for the synchronous mutation.
- **Pending runtimes never removed by maintenance**: `cleanup_idle`, `cleanup_orphaned_keepalive`, and `sync_status` now skip entries with `is_pending() == true`, preventing parked execution waiters from observing a spurious `RuntimeNotFound` while `create_runtime` is still in flight. `sync_status` uses an atomic `DashMap::remove_if` to close the prior TOCTOU window.
- **`registry.update` errors no longer swallowed**: `routes/runtimes.rs::create_runtime` previously called `.ok()` on the success-path `registry.update`, which silently orphaned the Docker container if the registry entry had been concurrently removed. Errors now propagate; the failure path tears down the container, removes the tmp folder, and fires `readiness_notify_and_remove` so any parked waiters get a deterministic 404 instead of waiting to deadline.
- **Atomic check-and-insert in `create_runtime`**: `registry.insert` now runs before `readiness_notifier(name)`, so a duplicate concurrent create returns `RuntimeConflict` (409) before any notifier or container resource is allocated. The R1 fallback in the readiness helper continues to handle waiters that arrive in the narrow window between `insert` and `notifier`.
- **`tmp_folder` path canonicalisation**: moved to the top of the volume-mount setup in `routes/runtimes.rs` so cleanup paths derive from the canonical base on hosts where `/var` is symlinked to `/private/var` (macOS), preventing stray temp directories on extraction failure.

### Changed
- **Parallel container adoption on startup**: `tasks::maintenance::adopt_existing_containers` previously issued `docker.inspect_container` calls for every managed container in series; now fans out via `futures::stream::buffer_unordered(min(16, num_cpus*2).max(4))`. Restart adoption time scales O(n / concurrency) instead of O(n).
- **Parallel runtime stats collection**: `tasks::stats::collect_stats` parallelises `get_container_stats` calls via `buffer_unordered(20)`.
- **Concurrency-bounded warmup**: `tasks::warmup::run_warmup` no longer spawns one task per image; uses `buffer_unordered(4)` with `resilience::retry_with_backoff` (3 attempts) per pull, matching the existing `pull_semaphore` capacity.
- **Single `list_containers` per maintenance cycle**: `run_maintenance` now calls `docker.list_containers(Some("urt.managed=true"))` once and threads `&[ContainerInfo]` to both `cleanup_orphaned_keepalive` and `cleanup_untracked_managed_containers`, halving the cycle's Docker RPC count.
- **Lower-cadence `sync_status` in log streaming**: `routes/logs.rs` log-buffer polling continues at 100ms but `sync_status` is only called every 3s (`LOG_SYNC_STATUS_INTERVAL`), eliminating the 2 RPC/100ms hot path under many concurrent streams.
- **`runtime_create_limiter` is always `Some`**: when `autoscale=false`, the create-runtime semaphore now holds `max(4, num_cpus)` permits instead of being unset, providing default backpressure against Docker daemon overload from create bursts.
- **Connect timeout on the runtime HTTP client**: `reqwest::Client::builder()` in `main.rs` now sets `.connect_timeout(Duration::from_secs(5))` so dead containers cannot hold connection slots open up to the full request deadline.
- **Per-request build timeout**: `routes/build.rs` accepts an optional `timeout` multipart field (1-900s, default 300s) and wraps `docker.build_image` in `tokio::time::timeout`. New `ExecutorError::BuildTimeout` variant maps to HTTP 504; existing build response schema preserved.
- **Retry-wrapped maintenance container removal**: `remove_container_for_cleanup` wraps `docker.remove_container` in `resilience::retry_with_backoff` (3 attempts, 100ms base). `RuntimeNotFound` is treated as terminal-success and not retried.

### Added
- **Optional blocking warmup**: `URT_WARMUP_REQUIRED` (default `false`). When `true`, the executor awaits image pre-pulls before binding the listener, eliminating cold-pull latency from the first wave of requests after startup. When `false`, warmup remains a background task as before.
- **Readiness-gate observability**: new histogram `urt_executor_readiness_wait_seconds` (label `outcome`=`ready`|`timeout`|`absent`), counter `urt_executor_readiness_timeout_total`, counter `urt_executor_network_attach_failures_total`. `wait_for_pending` records on every exit path so wait-time distribution and 504-from-readiness can be alerted on independently of network-side 504s.
- **Network-attach failure metric**: `docker::manager::connect_container_to_networks` increments `urt_executor_network_attach_failures_total{network, container}` on secondary network attach failure (existing best-effort behaviour preserved, now observable).
- **Shared readiness helper module**: new `crates/urt-executor/src/runtime/readiness.rs` exposing `pub(crate) wait_for_pending` and `pub(crate) async fn resolve_runtime_with_readiness`. Used by `executions.rs`, `commands.rs`, and `logs.rs` to deduplicate the readiness-gate logic.
- **18 new integration tests** under `tests/integration.rs` (`mod readiness_gate` and `mod audit_fixes`) covering: cold-start readiness, 504 timeout, 50-waiter storm, removal-while-waiting, pending-not-cleaned, notifier consistency, R1 pre-insert wake, commands/logs readiness wait, build-timeout error mapping, parallel adoption fan-out primitive, atomic create-runtime insert, readiness metric increment, `URT_WARMUP_REQUIRED` config parsing, retry-wrap transient handling.
